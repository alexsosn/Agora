# Agora 1.0 release plan

Agora 1.0 is a stability and usability release for the existing thin marketplace. The release target is the current four plugin families — Context-Fabric, Perseus, Sefaria, and SEDRA — plus the current Context-Fabric catalog. The release is not gated on a general package manager or on expanding the catalog.

The live tracker is [#148](https://github.com/alexsosn/Agora/issues/148).

## Release contract

A 1.0 candidate is ready when a first-time user can follow the public installation instructions, install a supported plugin, reach a representative successful research operation, understand relevant limitations and resource costs, and recover from common failures without reading Agora internals.

The candidate must satisfy these conditions:

- documented installation/launch works for every client/plugin path Agora claims as supported or verified;
- every advertised plugin exposes its expected tool surface and completes one representative real operation;
- known broken or misleading upstream operations are either fixed by consuming a reviewed upstream release or explicitly downgraded/documented in Agora's capability claims and facilitation guidance;
- Context-Fabric acquisition/load behavior is bounded by existing disk/resource safeguards, and long operations have understandable status/failure/cancellation behavior;
- feature-module overlay costs are disclosed and bounded before a user pays a parent-scale compile cost;
- README, installation, compatibility, and known-limitations documentation describe the release candidate rather than historical implementation plans;
- generated marketplace artifacts are fresh;
- release-critical CI and representative smoke checks pass on the frozen candidate head;
- `main` is protected by the required release CI gate;
- `v1.0.0` is published with concise release notes and known limitations.

## Active release work

The active release queue is intentionally small:

- #9 — protect `main` and require Foundation CI;
- #27 — make long Context-Fabric prepare/load operations understandable and bounded;
- #46 — disclose and bound expensive feature-module overlay loads;
- #149 — make advertised capabilities truthful against known upstream limitations;
- #150 — clean-install release candidate and first-time-user documentation audit;
- #148 — final release tracking, frozen-candidate verification, and publication.

Small, already-near-complete maintenance such as a reviewed registry pin update may merge during release preparation, but it does not expand the release contract.

## Deferred work

The following areas are deliberately post-1.0 unless new evidence shows that they directly break the release contract:

- general resource lifecycle/package-manager architecture, local install state, rollback, autoremove, and environment reconciliation;
- general dependency/capability solving;
- project manifests, lockfiles, and reproducible environment sync;
- third-party registry federation, namespaces, signing, and per-entity registry restructuring;
- automatic corpus release/version discovery and promotion;
- generic managed materialization artifact caches and Context-Fabric composition;
- Burns-specific parent-resource materializer orchestration;
- further Git metadata-maintenance optimization without a user-visible failure;
- CI queue optimization that does not affect release correctness;
- new plugin families and resource/catalog expansion.

Closed `not planned` issues retain the prior research and may be reopened after 1.0 when user demand or measured failures justify the work.

## Work-selection policy

Until #148 is complete, agents and contributors should choose work in this order:

1. incorrect/misleading user-visible results or invalid support claims;
2. clean install, launch, and first successful use;
3. data-loss, disk/memory, timeout, cancellation, and other stability hazards;
4. user-facing documentation and diagnostics;
5. regression prevention for the release contract;
6. final release hygiene and publication.

When one release item is blocked, choose another release item. Do not fill the gap with speculative platform architecture.

A newly discovered issue joins the 1.0 queue only when it can materially affect one of the first five categories above. Other findings should be recorded for post-release work without changing the release target.

## Development process during release mode

Use the risk-proportional gates in `AGENTS.md` and `CONTRIBUTING.md`.

TDD remains expected for behavior changes, and every finalized PR receives a logically independent adversarial review. Research and planning artifacts are required when they resolve genuine uncertainty or coordinate a multi-component/high-risk change. Small fixes, registry pins, generated metadata, and documentation changes should use the shortest evidence path that proves their user-visible contract.

Do not add unrelated acceptance criteria discovered during review to an in-flight release PR. A finding that does not block that PR or the 1.0 release should be recorded for later.

## Release-candidate sequence

1. Finish or explicitly downgrade/document the remaining user-facing correctness and stability limitations.
2. Run #150 from clean environments using the public docs.
3. Freeze the candidate revision; avoid feature additions after this point.
4. Run Foundation and the release-critical client/plugin/resource smokes on that exact revision.
5. Perform an independent release review centered on first-time-user behavior, truthful claims, stability, and scope control.
6. Resolve only release-blocking findings; park the rest.
7. Protect `main` as required by #9.
8. Publish the `v1.0.0` GitHub Release and update the front-page documentation from pre-release language to stable-release language.

## Definition of done

Agora 1.0 is done when the release contract above is true on the published tag. Completing the deferred architecture backlog is not part of that definition.

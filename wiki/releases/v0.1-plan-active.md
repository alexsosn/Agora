# Plan: Building Agora as a Digital Philology Marketplace

Agora is a fresh repository. `mcp-demo` is prior art and a source of reusable code/knowledge, not a compatibility target. The fixed first-implementation scope is defined in [`v0.1-scope-frozen.md`](v0.1-scope-frozen.md) and machine-enforced by `registry/v0.1.yaml`.

The plan deliberately separates three kinds of evidence:

1. **plugin/integration correctness** — can the client launch/connect, initialize MCP, enumerate the expected tools, and perform a representative real operation?;
2. **resource/runtime correctness** — can a registered corpus or collection be resolved/acquired/loaded through the provider?;
3. **upstream-documentation provenance** — can users identify the exact upstream source and documentation revision that governs corpus semantics, quality, and research suitability?

Plugin aggregate status, client-path status, resource/member evidence, and scholarly-data quality are separate claims. A stronger client-path result never promotes the aggregate plugin or its resources automatically.

## Phase 3 — Implement Context-Fabric and the 37-resource baseline

**Status: provider/runtime implementation complete; resource/member integration verification remains ongoing.**

Implemented:

- `plugins/context-fabric/` Python runtime around `cfabric-mcp==0.1.7`;
- generated Claude and Codex launch metadata;
- Agora MCP resource-management, cache-status, cancellation, pruning, removal, and unload tooling;
- generated runtime catalog from canonical registry data;
- lazy Git-backed source resolution and acquisition without machine-specific absolute paths in the registry;
- revision-addressed immutable source snapshots and source-revision provenance;
- explicit `prefer-fresh`, `offline`, and `require-fresh` source-resolution modes;
- deterministic TF dataset-root selection;
- optional pinned `ref` and `tf_path` support;
- collection-member discovery and independent loading rather than flattening each member into a marketplace plugin;
- commit-bound collection indexes and revision propagation through discovery, prepare, and load;
- collection-aware handling for `pthu/bible`, `pthu/patristics`, `pthu/greek_literature`, and `HuygensING/translatin-manif`;
- TLHdig-TF tracking upstream main, with an explicit `tf_path` selecting the published `tf/0.1.0` dataset;
- contained cold compilation with disk/time guardrails and cancellation;
- deterministic runtime/resolver/service/MCP tests;
- scheduled Git-metadata source audit over all 37 resources;
- representative real-corpus load smoke coverage, including known-failure retirement checks;
- live MCP startup/tool-discovery/catalog smoke through both generated client paths, plus bounded Linux, Intel-macOS, and Windows startup evidence for the local runtime package.

The implementation intentionally does not download every corpus on every ordinary CI run. Deeper resource/member evidence remains incremental and must stay distinct from plugin/client integration status.

**Provider exit criterion met:** the fixed 37-resource baseline is resolvable through one Context-Fabric provider and collection members are modeled as independently loadable corpora.

## Phase 4 — Implement Perseus, Sefaria, and SEDRA

**Status: implementations complete; verification is client-path scoped below.**

### Perseus

Implemented upstream-first integration with `tonyjurg/Perseus-mcp`:

- no vendoring or fork;
- pinned published package `perseus-mcp==1.0.2` launched through `uvx`;
- Claude and Codex MCP declarations;
- live MCP initialization and representative tool discovery through both generated client paths;
- representative Homer author-discovery lookup against upstream Perseus/Scaife resources.

### Sefaria

Implemented against the official Sefaria Texts MCP:

- Claude connects directly to `https://mcp.sefaria.org/sse`;
- current Codex configuration bridges the legacy SSE endpoint to stdio using `mcp-proxy==0.12.0`;
- the proxy runtime explicitly constrains `mcp>=1.17,<2` for integration compatibility;
- live MCP initialization and representative tool discovery through both generated client paths without substituting one transport for the other;
- representative retrieval of Genesis 1:1 in English.

### SEDRA

Implemented a small Agora-owned read-only FastMCP adapter over Beth Mardutho's public SEDRA IV JSON endpoints:

- no SEDRA data vendored;
- separate word and lexeme tools;
- transparent upstream JSON handling rather than invented morphology semantics;
- validation and error handling;
- deterministic tests for Syriac URL encoding and delegation;
- representative live Syriac word lookup through both generated client paths;
- bounded Linux, Intel-macOS, and Windows startup-only evidence for the packaged local runtime.

**Implementation exit criterion met:** all three integrations operate independently of Context-Fabric and have representative integration evidence. Current verification strength is recorded canonically per client rather than asserted here.

## Non-goals for v0.1

- preserving `mcp-demo` interfaces or workshop behavior;
- flattening individual Greek TF works into marketplace plugins;
- vendoring third-party MCP implementations unnecessarily;
- pretending all clients have identical transport capabilities;
- requiring Antigravity support in the first implementation;
- inventing licenses or hiding unknown licensing status;
- treating inclusion or integration verification as an assessment of upstream suitability or data quality.

## v0.1 definition of done

Agora v0.1 requires:

1. a working Context-Fabric plugin covering the fixed 37-resource baseline;
2. member-aware handling for large collection repositories;
3. working, independently installable Perseus, Sefaria, and SEDRA integrations;
4. deterministic Claude Code and ChatGPT/Codex marketplace manifests;
5. resource-level provenance, licensing, and integration-verification metadata;
6. representative integration tests;
7. plugin/resource guidance that directs users to authoritative upstream documentation;
8. contributor and end-user documentation.

The baseline for all eight items is implemented. Remaining v0.1 work is evidence/documentation depth rather than a missing marketplace core: current examples include deeper resource/member verification (#19) and targeted policy/documentation consolidation.

Reviewed after merge against `main` following:

- PR #4, **Address architecture review findings with TDD**, merge commit `197baa155badc062bf472083208b65fa2996a0c7`;
- PR #1, **docs: add post-v0.1 ecosystem backlog**, merge commit `c1db837a87dcc3b7a403d5053a72ffd851adc964`.

This is an independent review of the merged implementation and documentation, not a restatement of either PR description.

## Overall assessment

PR #4 materially improves the architecture reviewed earlier: trust metadata reaches the Context-Fabric runtime, floating Git sources refresh, resolved source revisions are exposed, launch metadata is declarative, network transports default to loopback, and verification is separated by client/transport. Those changes should be preserved.

However, the new mutable Git materialization design can produce a corpus directory whose bytes do not correspond to the `source_revision` reported to the client. That is a scholarly provenance/integrity bug and should be treated as the highest-priority engineering issue.

PR #1 is useful ecosystem research and does not look like wholesale README-driven hallucination. Its main weakness is representation: roughly 1,500 lines of candidate metadata and prioritization now live as prose rather than structured, evidence-bearing records. It should remain research input until candidates are independently verified and normalized.

# Findings on PR #4

## P0 / Critical — mutable materialization can report the wrong corpus snapshot

`GitStore.materialize()` checks out a selected path from a revision into one reused working tree and then returns that directory to the loader.

A path checkout from revision B does not necessarily remove files that were materialized from revision A but were deleted in B. Therefore the working directory can contain a mixture of old and new feature files while Agora reports only revision B as `source_revision`.

This was reproduced with ordinary Git behavior: materialize a directory from revision A, delete one tracked file in revision B, then run `git checkout --force B -- <directory>`; the obsolete file remains in the existing working directory.

There is a second race: the repository lock is released before `ContextFabricService.load()` reads the returned path. Another request can refresh/materialize the same resource while a loader is still reading it.

### Required direction

Materialized corpora should be immutable and revision-addressed, for example:

```text
<cache>/datasets/<resource-id>/<commit-sha>/<relative-dataset-path>/
```

Use a worktree/archive/export or another mechanism that guarantees the directory exactly represents that commit/path. `source_revision` must identify the bytes supplied to Context-Fabric, not merely the Git tree used by the most recent checkout operation.

### Missing regression tests

Add tests that:

1. materialize revision A with two feature files;
2. advance upstream to revision B deleting one feature file;
3. materialize B;
4. assert the deleted file is absent;
5. run concurrent load/materialize operations and assert one request cannot mutate another request's dataset snapshot.

## P0 / High — representative corpus-load smoke exists but is not executed by CI

PR #4 restores `scripts/smoke_context_fabric_resources.py` and defines BHSA, CUC, and Greek Iliad cases. No workflow file changed in the PR, and the current Foundation and Context-Fabric audit workflows do not invoke this script.

The earlier unfinished requirement — real corpus acquisition/materialization/load verification — therefore remains unfinished. The script exists, but it is dead with respect to CI evidence.

The smoke contract is also too weak: success currently means that `otype.tf` exists and the loader returned a non-`None` corpus object. It does not inspect actual text, nodes, source-specific features, or known scholarly values.

### Required direction

Wire representative load checks into a scheduled or appropriately scoped workflow and make each case assert real corpus semantics, e.g.:

- BHSA: retrieve a known passage/token and a known ETCBC feature;
- CUC: retrieve actual Ugaritic content and a CUC-specific feature;
- Iliad: retrieve a known passage/token and inspect a real morphology/text feature from the selected work.

## P0 / High — README verification claims contradict the canonical registry

PR #4 correctly changes aggregate plugin status to `community` because the Claude client paths have deterministic launch metadata but no equivalent live-client verification, while Codex paths are `verified`.

The root README still says that all four v0.1 plugin integrations are **Verified** by CI and describes the full live verification contract as applying to all four integrations.

The most visible trust claim therefore disagrees with the canonical registry.

### Required direction

Generate or validate user-facing verification summaries from canonical registry evidence. At minimum, add a CI consistency check so README claims cannot exceed registry status.

## P0 / High — collection discovery and loading are not snapshot-consistent

`list_members()` refreshes an upstream repository and enumerates members against revision A. The response does not expose or bind that revision. A later `prepare(member_id)` refreshes again and rebuilds the member map against revision B.

If the collection changed, the member the user inspected may disappear, move, or resolve differently.

### Required direction

Carry a snapshot token/revision across the workflow:

```text
list_members -> source_revision=A
prepare(member_id, source_revision=A)
load(member_id, source_revision=A)
```

Equivalent immutable snapshot semantics are acceptable, but user discovery and subsequent loading must be reproducible.

## P1 / Medium — filesystem lock can become permanently stale

The repository lock is an `O_CREAT | O_EXCL` sentinel containing a PID. It is removed in `finally`, but an abrupt process death can leave the file behind. Later processes wait for the timeout and fail; no stale-owner detection is performed.

Use an OS advisory lock/library released automatically when the process/file descriptor dies, or implement robust stale-lock detection.

## P1 / Medium — verification evidence is structured but not executable/traceable

The new evidence model records human-readable items such as a test name and `kind: live`, but it does not bind those claims to a workflow/test identifier, tested source/package revision, last successful run, or timestamp.

A plausible string can therefore claim evidence without machine linkage to the check that produced it.

### Required direction

Give checks stable IDs, for example `mcp-live/perseus-codex`, and have CI produce or validate evidence such as source revision, dependency set, and last successful run. Aggregate status should be derived from those records.

## P1 / Medium — provider status is forced to equal plugin aggregate status

The validator now requires provider verification status to equal the plugin's aggregate verification status. This removes stale contradictions but conflates different concepts.

A provider/service can be official and operational while a particular client adapter lacks live evidence. Conversely a verified adapter does not establish scholarly quality of all underlying resources.

Keep provider/service evidence, client integration evidence, and resource/data evidence as separate dimensions rather than enforcing equality.

## P1 / Medium — Greek author/title guessing is reduced, not eliminated

The previous deep-path heuristic was fixed for CTS-like paths, but paths with exactly two components are still automatically interpreted as `author/work`.

There is no general guarantee that a two-component repository identity has those semantics. Until a provider-specific parser or enriched member index supplies real metadata, return neutral identifiers rather than guessed author/title values.

## Process finding — large architectural PR merged with no meaningful review window

PR #4 changed 16 files with 17 commits and more than a thousand added lines, yet it was merged seconds after opening. The Foundation checks passed, but that is not an independent architectural review.

`main` also remains unprotected without required status checks. The earlier governance finding is therefore still open.

# What PR #4 fixed well

Preserve these decisions:

- canonical trust/licensing/known-issue metadata now reaches runtime responses;
- configured refs/paths and resolved Git revisions are exposed;
- floating sources no longer silently remain at the first clone forever;
- manually enabled HTTP/SSE transport defaults to loopback;
- plugin launch commands moved into validated registry metadata instead of central per-plugin Python branches;
- Claude and Codex verification evidence is separated;
- bogus semantic labels for deep Greek repository paths were removed;
- architecture-contract tests are substantially stronger than before.

The correct next step is another iteration of the cache/snapshot design, not a rollback of these improvements.

# Findings on PR #1

## P1 / High-Medium — the backlog is becoming a parallel unstructured database

The ecosystem, Egyptology, and Germanic surveys contain candidate identity, priority, provider, capabilities, licensing notes, scholarly status, caveats, overlap, and architecture recommendations in prose.

Agora's main architecture deliberately relies on canonical validated metadata, but candidate research now forms a second metadata system with no stable IDs or schema.

Questions such as the following should eventually be machine-answerable:

- which P0 candidates have unknown data licenses?;
- which candidates require authentication or paid access?;
- which have been installed and smoke-tested?;
- which claims were rechecked after a particular date?;
- which wrappers overlap the same upstream?;
- which candidates are wanted integrations rather than implementable MCPs?

### Required direction

Create structured candidate records with stable IDs and evidence fields, then use Markdown for commentary/synthesis. Do not promote README claims directly into the canonical plugin/resource registry.

## P1 / Medium — P0/P1/P2 currently collapses unrelated dimensions

The current priority system mixes scholarly value, institutional provenance, implementation readiness, breadth, and capability gaps. A highly important upstream with no stable API and a turnkey small MCP can therefore receive the same P-level for entirely different reasons.

Candidate evaluation should score at least:

- scholarly value;
- technical readiness;
- provenance/editorial authority;
- legal/licensing clarity;
- maintenance health;
- overlap with Agora;
- implementation effort.

Then derive implementation priority from those dimensions.

## P1 / Medium — licensing evidence is inconsistent across candidates

The backlog correctly says software, data, redistribution, and service terms are separate. Some candidate entries still omit material software-license facts or defer all licensing to later verification.

Use the same separation already present in Agora's canonical registry during candidate research, including non-standard software licenses and resource-specific content terms.

## P1 / Medium — annotation maturity needs explicit evidence, especially for Wulfila-like resources

The Germanic backlog correctly prioritizes Wulfila, but candidate descriptions should distinguish automatic annotation, manually reviewed/disambiguated annotation, snapshot dates, and work-in-progress datasets.

For language resources this distinction can materially affect whether morphology/POS data are suitable for research conclusions.

## P1 / Medium — upstream importance and integration readiness should be separate fields

Flagship resources such as TLA can be P0 scholarly targets while still requiring API/export/licensing feasibility work before implementation. The backlog should not visually imply that "we strongly want this" means "build this next".

Record both strategic importance and implementation readiness.

## P1 / Medium — candidate claims need evidence snapshots

A promotion workflow is documented, but individual candidate records usually lack explicit evidence such as:

- `checked_at`;
- upstream commit/tag/release;
- license source;
- observed MCP tool list;
- actual install/connect result;
- representative smoke result;
- data/provenance evidence URL.

These do not need academic-style footnotes in every paragraph, but they should exist before candidate promotion.

## P2 / Low — taxonomy proposals are not yet mapped to the registry model

The proposed classes (`lexicon-dictionary`, `htr-ocr`, `papyrology-epigraphy`, etc.) are useful but do not yet specify whether they are capabilities, disciplines, resource kinds, tags, or a new dimension.

Resolve that mapping before candidate implementations begin adding ad hoc vocabulary values.

# Recommended priority order

## P0 engineering

1. replace mutable Context-Fabric materialization with immutable commit-addressed dataset snapshots;
2. preserve collection revision across discovery → prepare → load;
3. execute representative BHSA/CUC/Iliad corpus-load checks in CI and validate actual content/features;
4. reconcile README verification claims with canonical per-client registry evidence;
5. enable required CI/branch protection;
6. bind verification evidence to executable checks and tested revisions.

## P1 engineering / trust model

7. replace crash-stale sentinel locking with robust advisory/stale-aware locking;
8. separate provider/service status from plugin/client status rather than forcing equality;
9. stop all generic author/title inference until semantic metadata is available;
10. lock/record runtime dependency environments where verification claims depend on them;
11. finish enriched collection indexes and member-level evidence.

## P1 ecosystem research

12. normalize backlog candidates into structured records with stable IDs and evidence snapshots;
13. separate scholarly importance, readiness, provenance, legal clarity, maintenance, overlap, and implementation effort;
14. only then promote selected candidates into release planning / canonical registry work.

## Review conclusion

PR #4 addresses a substantial fraction of the previous architecture review in the right direction, but the new Git materialization implementation makes floating-resource provenance insufficiently trustworthy until immutable snapshot semantics are implemented. PR #1 is valuable research, but should be treated as research input rather than a second informal registry.
